# 多设备协作测试方案

> 目标：在两台**真实物理电脑**上跑通多人、多 Agent 协作，并把结果留成可复核的证据。
>
> 本文主路径按 **Windows PowerShell** 写。macOS / Linux 也能跑，但必须把路径和启动命令换成对应写法。
>
> 事实边界先写清楚：
>
> - 本仓库已经验证过：同一台物理机、两个独立进程、两套独立状态目录、真实局域网地址、真实 relay、真实任务新增/认领/完成回传。
> - **尚未验证**：用户自己的第二台物理电脑、两台不同真实网络位置的物理机、Windows ↔ Linux/macOS、大规模并发、真实商户号到账、云上 24 小时托管分身。
> - **已额外验证（仍有边界）**：2026-11-08 用 Cloudflare Quick Tunnel 跑通公网 HTTPS MCP 与 relay 配对；两端是同一台物理机的两个独立安装，不是两台物理机。
> - 所以本文要求你在自己的两台机器上完成最后一步，而不是拿“同机模拟”冒充“真机已验收”。

## 0. 测试分层

| 阶段 | 环境 | 验什么 | 是否发布红线 |
| --- | --- | --- | --- |
| A | 单机 | 解包、安装、工具表、自动化基线 | 必须过 |
| B | 两台物理机、同一局域网 | 建房、进房、任务跨机回传 | **必须过** |
| C | 三台及以上 | 多人、席位、抢占式认领 | 建议过 |
| D | 跨公网 | HTTPS relay、长轮询 | 上线前单独验收 |
| E | 断网/重启/故障 | 降级、恢复、持久化 | 必须过 |

## 1. 两台机器都要准备的东西

### 1.1 运行环境

- Node.js **>= 22.12**
- 两台机器在同一 WiFi / 同一交换机下
- Windows 防火墙允许 Node 监听 **8787** 端口
- 两台机器都能访问对方局域网 IP

先查版本：

```powershell
node --version
```

如果低于 `v22.12.0`，先升级 Node，再继续。

### 1.2 准备同一份交付包

在任意一台有完整源码的机器上打包：

```powershell
Set-Location "C:\Users\LENOVO\Documents\Codex\2026-11-07\d-y\work\nexi\Nexi灵犀-完整项目"
npm pack --pack-destination .
Get-ChildItem .\agentdeck-super-1.11.4.tgz
```

把生成的 `agentdeck-super-1.11.4.tgz` 拷到两台机器。U 盘、微信文件、局域网共享都可以。

> 不要用旧的 tgz 代替这次打包结果。旧包里可能没有最新的测试、fixture 和文档。

## 2. 阶段 A：单机自动化基线

在任意一台已经解包的机器上：

```powershell
Set-Location .\package
node .\tools\verify-twomachines.mjs
```

期望结果是这一项自己的 28 条断言全部通过：

```text
28 项通过，0 项失败
```

这一步验的是：

- 一份包能被解成两个独立身份目录
- 两个身份能各自起 Hub
- 真实 relay 能建房间
- 第二个身份能凭邀请进房
- 任务能跨进程同步
- relay 重启后会话还能继续
- 跨机加密串门能走通

> 它仍然是在**一台物理机**上跑两个进程。看到 28/0 只能说明本机自动化过了，不能说明你的第二台电脑已经过。

## 3. 阶段 B：两台真实电脑，主验收

### 3.1 两台都解包

电脑甲：

```powershell
New-Item -ItemType Directory -Force -Path C:\nexi-A | Out-Null
Set-Location C:\nexi-A
tar -xzf <你拷来的>\agentdeck-super-1.11.4.tgz
Set-Location .\package
node .\bin\nexi.mjs doctor
```

电脑乙做同样的事，目录换成 `C:\nexi-B`。

如果系统 `tar` 因为路径里有中文而报错，先把 tgz 放到纯英文目录再解压；或者直接在源码目录里运行，不要依赖系统 tar。

### 3.2 电脑甲：一条命令起房

```powershell
Set-Location C:\nexi-A\package
node .\tools\nexi-pair.mjs host --tier business --seats 2
```

这个命令会：

1. 选择本机最可能被对面连上的局域网地址；
2. 在本进程里启动 relay，并绑定到 `0.0.0.0`；
3. 生成一张**本次配对专用**的协作版测试授权；
4. 建一个“真机配对小组”，再建一个绑定该小组的房间；
5. 打印可整段复制给电脑乙的中继地址和邀请链接。

**这个 PowerShell 窗口不要关。** 关掉后 relay 和房间都会消失。

如果选了虚拟网卡、或者你怀疑地址不对：

```powershell
node .\tools\nexi-lan.mjs
```

看输出里标着“局域网 / 用这个”的那一项。

### 3.3 电脑乙：用文件传邀请，避开 `&` 被 shell 吃掉

邀请链接里有 `&`。在 PowerShell / cmd 里直接拼 `--invite "http://...?...&t=..."` 有被 shell 拆开的风险。最稳的做法是存文件：

```powershell
Set-Location C:\nexi-B\package
@'
http://192.168.x.x:8787/?room=xxxx&t=yyyy
'@ | Set-Content -LiteralPath .\invite.txt -Encoding ascii
node .\tools\nexi-pair.mjs guest --invite-file .\invite.txt --name "乙机-测试"
```

把 `@'` 和 `'@` 之间的内容替换成甲机打印的网页形态邀请链接。不要保留尖括号占位符。

也可以用环境变量：

```powershell
$env:NEXI_INVITE = 'http://192.168.x.x:8787/?room=xxxx&t=yyyy'
node .\tools\nexi-pair.mjs guest --name "乙机-测试"
```

`guest` 会进房并调用一次 `sync`。客人**不需要授权码**，这是设计。每台设备使用同一个邀请、
不同的 `--name`，各自占 1 席。

### 3.4 两边核对

电脑甲和电脑乙各自执行：

```powershell
node .\tools\nexi-pair.mjs check
node .\tools\nexi-pair.mjs sync
```

通过标准：

- 两边 `check` 都能显示同一间房；
- 中继可达性显示“连得上”；
- 两边房间成员里能看到房主/客人；
- `sync` 不报“没有配置 relay”“连不上”“推送失败”。

> 当前 `deck_room` 只有 `create / join / sync / info / close / leave`，**没有 `send`、`pull` 这两个动作**。人和人之间的协作不是靠一个不存在的聊天动作，而是靠任务板和房间事件同步。

### 3.5 真正验跨机任务回传

这一段必须两边交替操作，不能只在甲机自说自话。

**甲机：新增任务**

```powershell
Set-Location C:\nexi-A\package
node .\tools\nexi-pair.mjs task add --title "乙机帮我看下日志" --acceptance "给出结论并回传"
node .\tools\nexi-pair.mjs sync
```

**乙机：拉取并看到任务**

```powershell
Set-Location C:\nexi-B\package
node .\tools\nexi-pair.mjs sync
node .\tools\nexi-pair.mjs task list
```

记下输出里的任务号，例如 `task_xxx` 或 `r_xxx`，后面用 `<任务号>` 代替。

**乙机：认领任务**

```powershell
node .\tools\nexi-pair.mjs task claim --id <任务号>
node .\tools\nexi-pair.mjs sync
```

**甲机：确认状态变成运行中**

```powershell
node .\tools\nexi-pair.mjs sync
node .\tools\nexi-pair.mjs task list
```

甲机应看到同一个任务，状态为 `running` 或等价的“已认领”，而不是还停留在 `pending`。

**乙机：完成任务并回传**

```powershell
node .\tools\nexi-pair.mjs task done --id <任务号> --output "已看完日志，根因是端口冲突"
node .\tools\nexi-pair.mjs sync
```

**甲机：确认完成和产出**

```powershell
node .\tools\nexi-pair.mjs sync
node .\tools\nexi-pair.mjs task list
```

通过标准：

- 甲机能看见乙机认领后的 `running`；
- 甲机能看见乙机完成后的 `done`；
- 完成产出里能看到乙机写的文字；
- 不是只在乙机本地成功、甲机毫无变化。

> 这一步是在最近一轮自检里专门补的。以前跨机只推送“新增任务”，不推送认领/完成状态，表现为“任务在乙机做完了，甲机永远没反应”。

### 3.6 席位和档位，不写“无限”

真实权益在 `lib/license.js` 的 `TIERS`：

| 档位 | 云房间 | 席位上限（含房主） | 并行 |
| --- | ---: | ---: | ---: |
| 免费版 | 0 | 3 | 1 |
| 协作版 `plus` | 20 | 8 | 3 |
| 工作室版 `studio` | 50 | 30 | 6 |
| 企业版 `business` | 200 | 200 | 10 |

`node tools/nexi-pair.mjs host` 默认自动签发一张 8 席的协作版测试授权。要做多设备项目验收，
显式写 `--tier business --seats N`（N 含房主，最大 200）；房主占 1 席，成员设备最多 N-1 台。
超过上限时 relay 返回 `room_full`，并说明“房间满员（上限 N 个席位）”。

免费版没有云房间，不能作为跨机房间房主；客人凭邀请进入别人的房间不需要授权码。

### 3.7 手工走 `deck_room` 时的正确姿势

如果不用 `nexi-pair`，而是通过 Hub 调原始工具：

```powershell
node .\bin\nexi.mjs call deck_room '{"action":"create","name":"双机测试","relayUrl":"http://<甲机IP>:8787"}'
```

乙机：

```powershell
node .\bin\nexi.mjs call deck_room '{"action":"join","inviteUrl":"<完整邀请链接>","memberName":"乙机-测试"}'
```

两边同步：

```powershell
node .\bin\nexi.mjs call deck_room '{"action":"sync","waitSec":0}'
```

注意：

- `join` 的参数名是 **`inviteUrl`**，不是 `url`；
- 没有 `send` / `pull`；
- 建房前必须让当前 Hub 读到有效授权。最推荐用 `/deck` 页面或 `deck_license` 动作激活；
- 手工写授权文件时，正确位置是 `$DSH_HOME\agentdeck-super\.agentdeck\license\key.txt`，不是旧文档里的 `work\.agentdeck\license\key.txt`。

如果你只是要做双机验收，优先用 `nexi-pair host`，它已经把测试授权、relay、房间和小组一起处理好了。

| 3 | 乙机进房 | 两边显示同一 `roomId` |

| 6 | 认领回传 | 甲机能看见 `running` |

## 4. 阶段 C：三台及以上

第一台仍按阶段 B 执行 `host --tier business --seats N`（N 是总席位，含房主）。
第二、第三台使用**同一条邀请链接**跑 `guest --name "姓名-部门"`，直到席位用尽。

多人协作的关键验收是抢占式认领：

1. 房主新增一条只应由一个人领取的任务；
2. 乙、丙几乎同时执行 `task claim --id <任务号>`；
3. 只允许一个成功，另一个必须收到“已被认领”或等价拒绝；
4. 所有机器各 `sync` 一次，最终状态必须一致。

如果出现两个人都显示认领成功，属于严重一致性缺陷，不能发布。

## 5. 阶段 D：跨公网

局域网测试通过后，才考虑跨公网。

relay 默认说 HTTP。公网必须放在 HTTPS 后面，否则邀请码、任务内容和同步令牌都可能被窃听。

推荐拓扑：

```text
客户端 -> https://nexi.example.com -> Nginx/Caddy -> 127.0.0.1:8787
```

Caddy 示例：

```text
nexi.example.com {
  reverse_proxy 127.0.0.1:8787
}
```

Nginx 至少要把长轮询超时放宽：

```nginx
location / {
  proxy_pass http://127.0.0.1:8787;
  proxy_read_timeout 300s;
}
```

验收至少包含：

- 浏览器打开 `https://你的域名/v1/plans` 证书有效；
- 两台不同网络的机器能建/进房；
- `sync` 长轮询不会被反代 504；
- 断网 30 秒恢复后仍能继续同步。

**2026-11-08 已用 cloudflared Quick Tunnel 做过真实公网 HTTPS 验收：**
`/healthz` 200、无 token 401、Bearer 握手 200、`tools/list` 23 个工具全过，
证据见 `docs/evidence/public-1.11.2.txt`。公网 relay 配对的历史证据
`docs/evidence/public-pair-1.11.1.txt` 仍只是同一台物理机的两个独立安装；
本版没有把它升格成“第二台物理机已验”。

你可以随时自己复验，一条命令：

```powershell
node tools\verify-public.mjs --provider cloudflared
```

它会起本地 MCP、开隧道、从公网侧验四项，全过才打印 `PASS`。

### 5.1 用插件命令接公网入口

如果你有现成域名/反代，可以直接：

```powershell
node tools\nexi-pair.mjs host --public-url https://nexi.example.com
```

插件会：
1. 本地起 relay（绑 `127.0.0.1:8787`）；
2. 探测 `https://nexi.example.com/healthz`；
3. 只有拿到 200 才建房并把邀请链接换成这个公网 origin；
4. 房主关房时连本地 relay 一起退出。

没有域名但有 `cloudflared` 时可以：

```powershell
node tools\nexi-pair.mjs host --tunnel cloudflared
node tools\nexi-pair.mjs host --public
```

注意：quick tunnel 的域名是临时的，进程关闭就失效，不能当长期服务地址。生产环境请用
自己的域名/反代、frp、Tailscale Funnel 或托管 relay；长期可用性由你自己的入口保证。

## 6. 阶段 E：故障与恢复

### 6.1 relay 重启

1. 甲机 `Ctrl-C` 停掉 `nexi-pair host`；
2. 用同一端口重新运行 `node tools\nexi-pair.mjs host`；
3. 让乙机使用新邀请重新 `guest`；
4. 两边 `sync`，检查历史任务是否还在。

> `nexi-pair host` 每次会建新房间；旧房间不会自动复活。这里验的是本地任务板不丢，不是“同一个邀请永远有效”。

### 6.2 本地降级

停掉 relay 后执行：

```powershell
node .\bin\nexi.mjs call team_board '{"action":"list"}'
```

通过标准：本地任务板仍可读，跨机操作给出明确错误，不挂死。

### 6.3 状态目录损坏

备份 `.nexi-pair` 后删掉它，再跑一次 `host` / `guest`。应能重建新状态，不把损坏的 JSON 当成有效房间继续用。

## 8. 故障速查

| 现象 | 先查什么 |
| --- | --- |
| 乙机连不上 | 两台是否同网段；甲机防火墙是否放行 8787；地址是否是虚拟网卡 |
| 只有 `127.0.0.1` | 机器没接真实局域网，接 WiFi/网线 |
| 邀请提示失效 | 链接抄错、`&` 被 shell 吃掉、房主窗口已关 |
| 建云房间被拒 | 当前档位没有云房间，换 `plus` 及以上 |
| `room_full` | 席位到上限，检查 `TIERS` 和房间成员 |
| 乙机看得到任务、甲机看不到认领 | 乙机 claim 后是否执行了 `sync`；甲机是否也执行了 `sync` |
| 重启后房间失效 | `nexi-pair host` 重启会建新房间，旧邀请不自动恢复 |
| `tar` 解包失败 | 路径含中文/空格；换纯英文路径，或直接用源码目录 |

## 9. 这套方案证明什么，不证明什么

**能证明：**

- 同一份包能在两个独立目录、两个独立进程、两套独立状态中启动；
- 真实局域网地址（本机网卡，非 127.0.0.1）上的 relay 能建房、进房、同步；
- 任务能跨机新增、认领、完成并回传；
- 席位上限会真实生效；
- 本地任务板在 relay 断开时仍可用；
- 加密串门不依赖 relay；
- 公网 HTTPS MCP 与 relay 配对已在本机双安装间跑通（Quick Tunnel 临时域名）。

**不能证明：**

- 你的第二台物理机已经通过（必须你自己跑）；
- 两台位于不同真实网络位置的物理机已经通过；
- 跨操作系统、大规模并发已经通过；
- 真实付款已经到账；
- 云上 24 小时托管分身已经上线；
- 桌宠能逐像素透明、鼠标穿透，或替代真的手机/桌面 App。

**“设计上支持”不等于“真机已验证”。这份文档不拿前者冒充后者。**
