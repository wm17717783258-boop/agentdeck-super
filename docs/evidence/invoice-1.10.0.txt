发票数据（1.10.0）取证
======================

结论：票面数据这一层做出来了——已付订单能开出编号稳定、字段齐全、可查可导出的发票记录。
      **但它不是税务合规的电子发票**，这一条写在每一份输出里，不靠文档口径兜着。

一、为什么定位成"发票数据"而不是"能开票"
  蓝图第 312 行把「发票、税费」列进真实支付门槛。真要开出合规发票，只有两条路：
    ① 走税务平台 / 税控设备（金税、航信这类）——需要资质；
    ② 让渠道开（Stripe 有 Invoicing，支付宝/微信有开票接口）——需要商户号。
  这两样本机都没有。所以这一层做的是**渠道或税务平台要什么字段，我们这边先备齐**：
  编号、抬头、税号、金额拆分、税额、行项目、渠道流水号，可查、可导出。
  **绝不假装已经能开票。**

二、做什么（lib/market/invoice.js）
  · 发票号 INV-<年月日>-<订单号后 6 位>：同一天同一单**稳定**（重开不换号），不同单不撞号。
  · 含税金额按税率**反算**不含税与税额，全程整数分运算（先乘后除再四舍五入），
    各种面额 × 各种税率都不出现"加起来差一分"。
  · 抬头：personal（可不填税号）/ company（**必须填税号**，不然拒——不生成缺税号的废票）。
  · 幂等：同一张订单重复开票返回原来那张，**不重复开、也不被第二次的参数改写**。
  · 落盘 <工作区>/market/invoices.json，原子写；文件坏了当空处理并在下次开票时重建。
  · 导出 JSON（给财务/渠道）。

三、怎么证明（不需要资质就能验）
  单元/集成：tests/invoice.test.mjs —— **13 条全过**
    税率反算（含 0/6%/13% 与各种面额不差分） / 税率乱给按未配处理 /
    发票号稳定不撞号 / 已付能开且字段齐全并落盘 / 重复开票幂等 /
    没付款不许开（created+refunded 都拒） / 订单不存在拒 / 公司抬头缺税号拒 /
    税率未配置明写"未配置" / 查询与导出对得上 / 坏文件不崩且能重建 /
    报告写清边界 / 常量表形状

  真机工具层（deck_market action=invoice）：
    · sub=issue 公司抬头 6% → INV-20261106-0001，¥18.00（不含税 ¥16.98 + 税额 ¥1.02）
    · 重复开 → 返回原来那张并明说"已经开过"
    · sub=list → 列出票号/订单/金额/抬头
    · 公司抬头缺税号 → 明确拒绝

  动作表：catalog / health / buy / orders / refund / reconcile / **invoice**

四、边界（照写，不美化）
  ✗ **不是税务合规的电子发票**：没有税控设备、没有税务平台对接、没有资质。
  ✗ **税率不自己编**：不填就是未配置，票面按不含税处理并**明写"税率未配置"**，
    绝不出现"已含税"这种没根据的说法。
  ✗ 不做税务法律判断（什么该免税、能不能抵扣）——只做"票面金额怎么拆"这一层算术。
  ✗ 不主动推送给税务平台 / 不生成 PDF / 不刻章。

五、门槛 ⑥ 现状（再更新）
    ✅ 支付链路（真 HTTP → 回执 → 发放 → 幂等 → 退款冲正）
    ✅ Webhook 幂等 + 验签
    ✅ 对账（reconcile-1.10.0.txt）
    ✅ **发票数据**（本文件）—— 票面字段备齐，可查可导出
    ❌ **真实商户号**：没有。未配一律回「环境未配」，订单停在 created，不编流水号。
    ❌ **税费**：只有"按税率拆分票面金额"这一层算术；**申报/缴纳/抵扣没做**，
       也不该由客户端插件做。
    ❌ 主动去渠道拉流水：没验过。
  所以对外仍然**不许**说「真实支付」——只能说「链路通、只差一个商户号」。
