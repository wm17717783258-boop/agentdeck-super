# 多设备席位测试 · 极简版

> 目标：让任意数量的物理设备，用同一个安装包、同一个项目房间、同一张任务板协作。
> 当前版本：`1.11.4`。

---

## 0. 先看结论

| 问题 | 现在的真实答案 |
| --- | --- |
| 能不能多台物理设备一起测 | 能。`nexi-pair host --tier business --seats N` 可开测试席位 |
| 能不能无限设备 | **不能。** 企业版硬上限 200 席；真正无限需要持久 relay、管理员席位池、签发/回收和审计，不是把数字改成 `Infinity` |
| 能不能所有 Agent 在插件市场搜索安装 | **现在不能承诺。** GitHub 仓库公开，但 GitHub Release、npm、MCP Registry 还没有同步到 1.11.4；npm 查询 `agentdeck-super` 仍是 E404，MCP Registry 同名查询仍是 0 条 |
| 最方便的测试分发 | 公司共享盘 / GitHub Release 放同一个 `.tgz`，每台设备校验 SHA256 后解包 |
| 适不适合大型项目正式使用 | 当前适合协议和协作验收，不适合作为“无限坐席”的生产控制面 |

别把“支持 MCP”说成“所有 Agent 自动支持”。支持 MCP 的宿主可以接入；不支持的宿主需要适配器。

## 1. 测试包怎么发给所有设备

### 最简单：共享盘或 GitHub Release

只发一个文件：

```text
agentdeck-super-1.11.4.tgz
SHA256SUMS.txt
```

每台设备做同一件事（不要给每台设备打不同的包）：

```powershell
# 1) 校验
Get-FileHash .\agentdeck-super-1.11.4.tgz -Algorithm SHA256
# 对比 SHA256SUMS.txt

# 2) 解包到独立目录
New-Item -ItemType Directory -Force C:\nexi | Out-Null
Set-Location C:\nexi
tar -xzf <下载目录>\agentdeck-super-1.11.4.tgz

# 3) 自检 + 接入本机宿主
Set-Location .\package
node .\bin\nexi.mjs doctor
node .\bin\nexi.mjs install --all
```

要求：Node.js `>= 22.12.0`。

`install --all` 只覆盖本机已安装的已知宿主。没有列出来的 MCP 宿主，用 README 里的手动配置接同一份 `stdio` MCP 服务。

## 2. 房主：一条命令开项目房间

先按规模选总席位（**房主也算 1 席**）：

| 总设备数 | 命令里的 seats |
| ---: | ---: |
| 2 | `--seats 2` |
| 3 | `--seats 3` |
| 10 | `--seats 10` |
| 50 | `--seats 50` |
| 最大 200 | `--seats 200` |

房主设备执行：

```powershell
Set-Location C:\nexi\package
node .\tools\nexi-pair.mjs host --tier business --seats 10
```

它会：

1. 选真实局域网网卡，不用 `127.0.0.1`，也不把 `198.18.0.1` 当可用地址；
2. 起 relay，监听 `0.0.0.0:8787`；
3. 临时签一张**本次配对专用**的企业版测试授权；
4. 建房并打印邀请链接和“可加入几台客人设备”。

输出里必须有：

```text
测试授权：企业版 / 10 席（仅本次配对，非生产授权）
席位口径：房主占 1 席，最多还可加入 9 台设备
```

**房主窗口不能关。** 现在 relay 跑在这个进程里，关掉房间就没了。

## 3. 所有成员设备：一行加入

把邀请链接保存成文件，避免 PowerShell 把 `&` 当命令分隔符。每台设备只跑一次：

```powershell
Set-Location C:\nexi\package
notepad .\invite.txt   # 粘贴房主给的邀请链接，保存
node .\tools\nexi-pair.mjs guest --invite-file .\invite.txt --name "张三-设计部"
```

成功的输出必须包含：

```text
进房并同步成功
```

`--name` 只用于房间里的成员显示，不参与授权。每台设备必须起一个不重复的名字，
例如 `张三-设计部`、`李四-财务`、`CI-Windows-03`，房主才能在名单里分清谁是谁。
每台设备解包到自己的目录即可，不需要房主发授权码。每台设备进房占 1 席。

房主可以随时看项目席位名单：

```powershell
node .\tools\nexi-pair.mjs members
```

### 3.1 公司项目怎么分配席位（当前最简做法）

当前没有“管理员按员工单独签发不同邀请”的控制面，所以公司测试用**一个项目房间 +
一份邀请链接 + 一张带姓名的席位表**，不要再制造多套房间：

| 员工/设备 | 席位名 | 谁发链接 | 进房命令 |
| --- | --- | --- | --- |
| 项目负责人 | `王五-项目经理` | 房主 | 房主自己占 1 席 |
| 设计 | `张三-设计部` | 房主 | `guest --name "张三-设计部"` |
| 财务 | `李四-财务` | 房主 | `guest --name "李四-财务"` |
| CI/测试机 | `CI-Win-03` | 房主 | `guest --name "CI-Win-03"` |

注意：这条邀请是**占席凭证**。拿到链接的人在满房前都能占 1 席；要撤掉某个人，
目前只能让那台设备 `leave`，或者房主关房后重新开房。真正的“按员工签发/单独撤销”
属于下一阶段的生产控制面，不是当前已经有的能力。

## 4. 五个物理验收动作

### A. 网络先证可达

房主先看实际 WiFi/网线地址：

```powershell
Get-NetIPConfiguration | Select-Object InterfaceAlias,IPv4Address
```

选 `192.168.x.x` 或 `10.x.x.x`，不要用 `127.0.0.1` 或 `198.18.0.1`。

另一台设备执行：

```powershell
Test-NetConnection 192.168.x.x -Port 8787
```

`TcpTestSucceeded : True` 才算网络通。

Windows 防火墙没放行时，房主可选执行：

```powershell
New-NetFirewallRule -DisplayName "Nexi Relay 8787" -Direction Inbound -Protocol TCP -LocalPort 8787 -Action Allow -Profile Private
```

测完回滚：

```powershell
Remove-NetFirewallRule -DisplayName "Nexi Relay 8787"
```

### B. 每台都核对房间和席位

每台设备：

```powershell
node .\tools\nexi-pair.mjs check
```

验收点：

- 中继显示“连得上”；
- 每台都能看到同一个房间；
- 房主看到成员数随设备加入增长；
- 第 `N+1` 个设备进不来，并明确显示房间满员。

### C. 跨设备任务闭环

房主：

```powershell
node .\tools\nexi-pair.mjs task add --title "跨设备验收-01" --acceptance "成员设备领取并回传结果"
node .\tools\nexi-pair.mjs sync
```

成员设备：

```powershell
node .\tools\nexi-pair.mjs sync
node .\tools\nexi-pair.mjs task list
node .\tools\nexi-pair.mjs task claim --id <本机列表里的任务号>
node .\tools\nexi-pair.mjs task done --id <同一个任务号> --output "本机已完成并回传"
node .\tools\nexi-pair.mjs sync
```

房主：

```powershell
node .\tools\nexi-pair.mjs sync
node .\tools\nexi-pair.mjs task list
```

验收点：房主看到状态从 `pending` → `running` → `done`，且产出文本是成员设备写的那句。

### D. 并发认领

同一任务让 3 台设备同时 `task claim`。只能有一台成功，其余必须失败。这是“多人协作”不重复干活的底线。

### E. 断线

房主按 `Ctrl-C`，成员设备再 `check`：

- 必须提示连不上；
- 本机任务板不能崩，不能丢数据；
- 重新起 host 会生成新房间和新邀请，旧邀请不能继续用。

最后一条是当前限制，不是 bug：relay 还没有持久化到独立服务。

## 5. 推荐扩容顺序

不要第一天直接上 50 台。按下面顺序：

| 轮次 | 规模 | 目的 |
| --- | --- | --- |
| 1 | 2 台（房主 + 1） | 证明两台物理机可达、进房、任务回传 |
| 2 | 3 台 | 证明多成员、并发认领 |
| 3 | 10 台 | 证明席位、连接和同步不靠偶然 |
| 4 | 50 台 | 大型项目预演 |
| 5 | 200 台 | 企业上限压力测试，单独排期 |

每一轮都记录：设备名、系统、IP、Node 版本、命令、截图、失败原文。

## 6. 发现问题后的修改闭环

不要直接改解包目录后让所有设备“再试试”。固定流程：

```powershell
Set-Location <源码目录>
node tools/test-summary.mjs
npm pack --pack-destination .
Get-FileHash .\agentdeck-super-1.11.4.tgz -Algorithm SHA256
```

把新 `.tgz` 和新的 SHA256 发回所有设备，重新解包到新目录再测。这样能保证大家测的是同一版。

如果改了版本号，Release、`SHA256SUMS.txt`、测试记录必须一起更新。

## 7. GitHub / 插件市场到底怎么做到“搜索安装”

要做的是三件不同的事，不能混成一句：

1. **GitHub Release**：分发可下载的 `.tgz` 和校验值。适合内部测试，最稳定。
2. **npm 包**：让 `npx agentdeck-super` / `dsh plugin add` 真正可用。
3. **MCP Registry / 插件市场**：让支持 MCP 的宿主能发现。需要发布 `server.json`，通过审核或索引后才可能出现搜索结果。

当前事实（2026-11-09）：

- GitHub 仓库是公开的，但 Release 还没有同步到 1.11.4；
- npm 查询 `agentdeck-super` 返回 E404；
- MCP Registry 查询该名称返回 0 条；
- 因此**现在不能承诺在任意 Agent 市场搜索到并安装**。

在完成 npm 发布、MCP Registry 收录和 Release 更新之前，最方便的真实测试方式就是第 1 节的统一下载 + 解包。
这几件事是分发问题，不是协议问题；测试房间本身不依赖 npm 或 MCP Registry。

## 8. 企业席位还缺什么

当前做到的是：

- 一个项目房间；
- 最多 200 席；
- 每个设备凭同一邀请占一个席位；
- 房主能看到成员和任务；
- 有人离开可释放席位。

还没做到：

- 公司管理员按员工姓名签发独立席位；
- 单独撤销某个员工的席位；
- 项目级席位池跨房间复用；
- 常驻 relay / 高可用；
- SSO/SCIM、多租户隔离、审计中心。

所以现在适合“真实多设备项目验收”，不适合直接对外卖“无限席位”的生产方案。要无限，必须新增持久的项目席位控制面，而不是把 `maxSeats` 改大。

### 8.1 从 200 席扩到真正不限席的最短路线

1. 先部署常驻 relay（VPS / 公司服务器 / 云主机），不要用房主进程内嵌的临时 relay；
2. relay 增加项目、席位池、成员邀请、撤销、审计和多租户隔离；
3. 每台设备只拿到自己的短期席位令牌，不再共用一条永久的房主邀请；
4. 公司管理员看席位占用、回收、过期和项目隔离；
5. 再用同一套 `nexi-pair` 命令做多设备压力测试。

这一步不能靠改 `maxSeats` 完成。先把这五步做完，才有资格对外说“无限席位”。
